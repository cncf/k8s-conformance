# Mirantis Kubernetes Engine 4.2.0

The Mirantis Kubernetes Engine 4.2.0 is made up of a number of
components, including Kubernetes v1.35.

## Installing Mirantis Kubernetes Engine 4.2.0 to reproduce the results

You will need to deploy a cluster of 1 or more nodes. Mirantis recommends using [mkectl](https://docs.mirantis.com/mke-docs/docs/getting-started/install-mke-4k-cli/) to ease the provisioning and installation of an MKE 4.2.0 cluster.

### Provisioning a Cluster with mkectl

The following section assumes that you have provisioned some instances with the necessary specifications defined in [System Requirements](https://docs.mirantis.com/mke-docs/docs/getting-started/system-requirements/).

1. Install the MKE 4.x CLI. More details at [Install the MKE 4k CLI](https://docs.mirantis.com/mke-docs/docs/getting-started/install-mke-4k-cli/)

2. Create the MKE 4.x configuration file

    MKE 4 clusters are configured using a YAML file. By default `mke4.yaml` is used as the name of the MKE 4 config file, unless it is explicitly specified.

    Detailed steps for creating the MKE 4 configuration file can be found at [Mirantis Kubernetes Engine 4k Initialize Deployment](https://docs.mirantis.com/mke-docs/docs/getting-started/create-cluster/#initialize-deployment). Details of the configuration specification can be found at [Mirantis Kubernetes Engine 4k Configuration](https://docs.mirantis.com/mke-docs/docs/configuration/).

    ```bash
    mkectl init > mke4.yaml
    ```

    This submission used one `controller+worker` host and three `worker` hosts.

    Three values need to be set in the generated configuration so that the
    conformance tests can reach the cluster on the ports they expect:

    1. Set `spec.network.nodePortRange` to the Kubernetes default range. The
       upstream end-to-end tests allocate NodePorts from a hardcoded
       `30000-32767` range, so a cluster installed with any other range fails
       the NodePort tests:

        ```yaml
        spec:
          network:
            nodePortRange: 30000-32767
        ```

    2. Set the MKE ingress NodePorts so that they fall inside that range. In
       MKE 4.2.0 the ingress is configured under `spec.gatewayMKEIngress`
       (`spec.ingressController` is disabled by default and is not the setting
       to change):

        ```yaml
        spec:
          gatewayMKEIngress:
            nodePorts:
              http: 30000
              https: 30001
        ```

    3. Set `spec.apiServer.externalAddress`. MKE 4.2.0 requires an external
       address. If you do not have an external load balancer in front of the
       manager node(s), enable `controlPlaneLoadBalancing` and use that as the
       external address instead:

        ```yaml
        spec:
          apiServer:
            externalAddress: "<load-balancer-dns-name>"
        ```

    An example `mke4.yaml` for a four-host cluster looks like this (only the
    fields relevant to the settings above are shown; the rest of the file is
    as generated by `mkectl init`):

    ```yaml
    apiVersion: mke.mirantis.com/v1alpha1
    kind: MkeConfig
    metadata:
      name: mke
      namespace: mke
    spec:
      apiServer:
        externalAddress: "<load-balancer-dns-name>"
      network:
        nodePortRange: 30000-32767
      gatewayMKEIngress:
        nodePorts:
          http: 30000
          https: 30001
        ports:
          http: 80
          https: 443
      hosts:
      - role: controller+worker
        ssh:
          address: <manager-address>
          keyPath: <path-to-ssh-private-key>
          port: 22
          user: <ssh-user>
      - role: worker
        ssh:
          address: <worker-1-address>
          keyPath: <path-to-ssh-private-key>
          port: 22
          user: <ssh-user>
      - role: worker
        ssh:
          address: <worker-2-address>
          keyPath: <path-to-ssh-private-key>
          port: 22
          user: <ssh-user>
      - role: worker
        ssh:
          address: <worker-3-address>
          keyPath: <path-to-ssh-private-key>
          port: 22
          user: <ssh-user>
    ```

3. Bootstrap your cluster

    ```bash
    mkectl apply -f mke4.yaml
    ```

4. Once the above command has completed successfully, you will see the Admin UI
   connection information.

### Setting up your environment

1. Log in to one of the manager nodes and obtain the kubeconfig for the cluster:

    ```bash
    sudo k0s kubeconfig admin > ~/.kube/config
    chmod 600 ~/.kube/config
    export KUBECONFIG=~/.kube/config
    ```

2. Ensure that `kubectl` is available on the PATH.

3. Confirm, by running an arbitrary `kubectl` command, that `kubectl` is able to
   access the cluster with the above `KUBECONFIG`.

    ```bash
    kubectl get nodes
    ```

## Run Conformance Test

1. Install the Sonobuoy CLI from [https://github.com/vmware-tanzu/sonobuoy](https://github.com/vmware-tanzu/sonobuoy). v0.57.5 was used for this submission.

2. Launch the conformance tests

    ```bash
    sonobuoy run --mode=certified-conformance --kubernetes-version=v1.35.4
    ```

    The MKE manager node carries the standard
    `node-role.kubernetes.io/control-plane` taint, which is the default value of
    the end-to-end framework's `--non-blocking-taints`, so no additional plugin
    environment is required.

    Follow the progress of the run with:

    ```bash
    sonobuoy status
    ```

3. Once the tests are complete, retrieve the results

    ```bash
    outfile=$(sonobuoy retrieve)
    mkdir -p results
    tar xzf "$outfile" -C results
    cp results/plugins/e2e/results/global/e2e.log .
    cp results/plugins/e2e/results/global/junit_01.xml .
    ```

4. (Optional) Clean up the Kubernetes objects created by Sonobuoy

    ```bash
    sonobuoy delete --wait
    ```
